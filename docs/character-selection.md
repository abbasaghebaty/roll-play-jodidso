# سیستم انتخاب کاراکتر خصوصی

## مسئولیت ماژول‌ها

| مسیر | مسئولیت |
|---|---|
| src/data/catalog/characters/ | داده ثابت کاراکترها بر اساس فرنچایز |
| src/data/catalog/techniques/ | داده ثابت تکنیک‌ها بر اساس فرنچایز |
| src/data/catalog/defenses/ | داده ثابت دفاع‌ها |
| src/data/registry/ | جست‌وجو و دسترسی مرکزی با ID، Code و کلید سازگاری قدیمی |
| src/data/validation/ | بررسی شناسه‌ها، کدها، مقادیر و ارتباط کاراکتر/تکنیک |
| src/game/selection/requests.js | ساخت Session، ساخت لینک، چرخه عمر درخواست و ثبت اتمیک انتخاب در D1 |
| src/game/selection/resolver.js | پردازش متن پیوی، نتایج جست‌وجو، صفحه‌بندی، تأیید و callback انتخاب |
| src/game/ui/panel.js | ساخت دکمه URL مشترک Lobby؛ پنل گروه فهرست کاراکترها را نمایش نمی‌دهد |
| src/commands/index.js | جداکردن پیام‌های معمولی پیوی از فرمان‌های گروه و مسیریابی callbackهای انتخاب |

## مدل Session و امنیت لینک

- هر /newgame یک شناسه تصادفی ۱۲۸ بیتی در games.session_id می‌سازد.
- Hash با SHA-256 در games.selection_token_hash ذخیره می‌شود.
- payload لینک به شکل cs_<session_id> است و در محدودیت ۶۴ کاراکتری Telegram جا می‌گیرد.
- لینک Lobby برای همه اعضای گروه مشترک است و فقط Session را معرفی می‌کند؛ مجوز انتخاب یک کاربر نیست.
- پس از /start در Private Chat، یک ردیف مستقل در character_selection_requests با request_id تصادفی، user_id، private_chat_id، chat_id و session_id ساخته می‌شود.
- درخواست قبلی همان کاربر برای همان Session لغو می‌شود؛ درخواست کاربران دیگر مستقل می‌ماند.
- لینک Session هفت روز اعتبار دارد. هر درخواست خصوصی سی دقیقه اعتبار دارد.
- /newgame شناسه و Hash تازه می‌سازد و درخواست‌های باز قبلی را لغو می‌کند.
- شروع یا پایان بازی درخواست‌های باز همان Session را لغو می‌کند. حتی در صورت باقی‌ماندن callback قدیمی، وضعیت بازی و Session در زمان ثبت دوباره بررسی می‌شوند.
- درخواست به کاربر و Private Chat متصل است؛ callback کاربر دیگر یا پیام گروه پذیرفته نمی‌شود.
- توکن Session یک‌بارمصرف برای کل گروه نیست. این رفتار عمدی است تا استفاده نفر اول لینک را برای دیگر اعضا خراب نکند.

## چرخه انتخاب

1. کاربر دکمه انتخاب کاراکتر را در Lobby می‌زند.
2. Telegram دستور /start cs_<session_id> را در پیوی می‌فرستد.
3. Worker Hash شناسه را بررسی می‌کند و وجود Session باز و منقضی‌نشده را می‌سنجد.
4. درخواست مستقل کاربر در D1 ساخته می‌شود.
5. متن بعدی کاربر فقط در صورت داشتن درخواست pending فعال به جست‌وجو می‌رود.
6. Registry تطبیق دقیق کد، شناسه، نام فارسی/انگلیسی و سپس پیشنهاد تقریبی را انجام می‌دهد.
7. نتایج با دکمه و صفحه‌بندی نمایش داده می‌شوند؛ fuzzy match هرگز خودکار انتخاب نمی‌شود.
8. انتخاب اولیه فقط candidate را در درخواست ثبت می‌کند؛ ثبت بازیکن نیازمند تأیید نهایی است.
9. ثبت نهایی با D1 batch انجام می‌شود و وضعیت Session و درخواست در همان عملیات دوباره کنترل می‌شود.
10. پنل گروه پس از موفقیت به‌روزرسانی می‌شود؛ پیام‌های جست‌وجو و تأیید در پیوی می‌مانند.

## تغییر کاراکتر و منابع

- کلید بازیکن (chat_id,user_id) ثابت می‌ماند؛ انتخاب کاراکتر تکراری بین چند کاربر مجاز است.
- در تغییر کاراکتر، char_key و سقف‌های max_hp/max_np به مقادیر Catalog کاراکتر جدید تغییر می‌کنند.
- HP و NP جاری با مقدار پایه کاراکتر جدید جایگزین نمی‌شوند؛ هرکدام فقط با سقف جدید محدود می‌شوند.
- name، team، seat، alive، poisoned، drained، last_tech و spam دست‌نخورده می‌مانند.
- پس از Deploy نسخه جدید، اولین پیام یا callback گروه `syncPlayerCatalogCaps` را اجرا می‌کند. این همگام‌سازی سقف را در صورت افزایش مقدار Catalog بالا می‌برد، اما سقف بالاتر ذخیره‌شده را حفظ می‌کند تا سقف افزایش‌یافته با `/buff` از بین نرود. HP/NP جاری فقط در صورت بالاتر بودن از سقف ذخیره‌شده محدود می‌شوند؛ هرگز از این مسیر افزایش نمی‌یابند.
- مقدار پایه Catalog از سقف افزایش‌یافته باف‌شده جداگانه ذخیره نمی‌شود؛ بنابراین کاهش مقدار پایه در Catalog به‌صورت خودکار سقف بازیکنان موجود را پایین نمی‌آورد. انتخاب مجدد کاراکتر سقف را دقیقاً به مقدار فعلی Catalog برمی‌گرداند.
- تغییرات `/buff hp` و `/buff np` به‌صورت افزایش/کاهش اتمیک در D1 اعمال می‌شوند؛ مقدار HP/NP که پیش از تغییر خوانده شده باشد مبنای نوشتن مجدد قرار نمی‌گیرد. بنابراین دمیج یا مصرف NP هم‌زمان با باف با مقدار قدیمی overwrite نمی‌شود.
- تکنیک‌ها و دفاع‌ها از Catalog همان نسخه Worker خوانده می‌شوند؛ برای بازی فعال Snapshot ثابت ساخته نمی‌شود.

## تنظیم نام کاربری

در wrangler.toml و فقط در بخش [vars] مقدار BOT_USERNAME را تنظیم کنید. مقدار فعلی abbas_developerbot است. هیچ ماژول دیگری نباید نام کاربری ربات را ثابت نگه دارد. buildSelectionUrl مقدار را اعتبارسنجی می‌کند و در صورت نبودن/نامعتبر بودن تنظیم، URL ناقص تولید نمی‌کند.

## Migration

ساختار D1 از طریق Migrationهای نسخه‌بندی‌شده در `migrations/` مدیریت می‌شود. Migrationهای این قابلیت از طریق سیستم رسمی Wrangler اجرا می‌شوند؛ دستورها، راه‌اندازی دیتابیس تازه، و روش Adopt کردن دیتابیس قدیمی در بخش [Migrationهای D1 در README](../README.md#migrationهای-d1) توضیح داده شده‌اند.

برای دیتابیس موجود، قبل از اجرای Remote باید وضعیت واقعی Schema و سابقه Migrationهای قبلی بررسی شود؛ ثبت اشتباه Migrationهای قدیمی به‌عنوان اعمال‌شده یا اجرای دوباره `ALTER TABLE` می‌تواند باعث شکست شود. Migration Remote از این مخزن اجرا نشده است.

## Catalog ناقص

در داده اصلی Repository برای ماکی، یوجی و دامی نام کامل انگلیسی وجود نداشت. بنابراین فیلد name.en برای آن‌ها null است و Validator آن را به‌صورت warning گزارش می‌کند. برای جست‌وجوی انگلیسی، نام انگلیسی معتبر باید از منبع داده دریافت شود؛ این پروژه نباید ترجمه یا املای حدسی را به‌عنوان داده قطعی جا بزند.

## آزمون

```sh
node --experimental-default-type=module --test tests/*.test.mjs
```

آزمون‌های private-selection.test.mjs رفتار Session، لینک، مالکیت درخواست، انقضا، تغییر کاراکتر، حفظ منابع، انتخاب تکراری، Migration و همگام‌سازی سقف Catalog را پوشش می‌دهند. آزمون‌های catalog-search.test.mjs اولویت تطبیق، نرمال‌سازی، فاصله ویرایشی و صفحه‌بندی را بررسی می‌کنند.
